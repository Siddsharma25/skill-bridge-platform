# skill-bridge-platform

Job/skill-gap matching platform. Learning-focused polyglot microservices monorepo — see `docs/DECISIONS.md` for the full architecture and the reasoning behind every non-obvious choice before making structural changes.

## Stack

- **frontend/** — React 19 + Vite + TypeScript + Tailwind + shadcn/ui + TanStack Query + Zustand + React Hook Form + Zod + React Router.
- **backend/** — Go microservices (`auth`, `users`, `skills`, `jobs`, `api-gateway`), gRPC via proto-first `buf` codegen, GraphQL gateway via `gqlgen`, GORM + Supabase Postgres.
- **backend/notification-service/** — NestJS, consumes RabbitMQ only.
- **docker/**, **k8s/**, **jenkins/** — local infra/orchestration practice, not the production deploy path (Render + Vercel is).

## Commands

```
# frontend
cd frontend && npm run dev / npm run build / npm run lint

# backend (once scaffolded — see backend/CLAUDE.md)
cd backend && make gen        # regenerate gRPC/gqlgen stubs after editing a .proto or GraphQL schema
cd backend && make test
cd backend && make lint
```

## Conventions

- `backend/gen/` is generated by `buf generate` and **committed** — never hand-edit it, run `make gen` instead.
- Every Go service gets health/readiness endpoints, graceful shutdown, and `x-request-id` propagation from `internal/platform` — these aren't optional per-service boilerplate to skip.
- Each service/module has its own short README explaining what it does and why it's built that way — update it alongside the code, don't batch it at the end.
- Nested `frontend/CLAUDE.md` and `backend/CLAUDE.md` hold stack-specific conventions; this file stays high-level.
- **Whenever a new doc is created anywhere in this repo (a new README, a new file under `docs/`, etc.), add it to `docs/INDEX.md`** in the same commit — that file is the map of every document in the repo, and it's only useful if it's actually complete. Don't batch this for later.

## Efficiency conventions for background agents (any part of this repo)

Applies whether the work is backend, frontend, docker/k8s, or CI — not Go-specific:

- **If resuming interrupted work, you were almost certainly resumed via `SendMessage` to your own prior instance, not spawned fresh** — trust the context you already have rather than re-reading the plan file, this CLAUDE.md, and `docs/DECISIONS.md` in full again "to be safe." A cold fresh-agent restart re-pays the full context cost every time; that was the single biggest source of wasted spend across early phases.
- **Reserve full live end-to-end proof (spinning up the whole stack, a real browser, a hand-rolled protocol client, etc.) for the 1-2 things that are the actual architectural point of the current task.** Routine plumbing (a queue DLQ-routing one malformed message, a cache returning a hit, a form validating one bad input) is adequately proven by a solid unit/integration test — don't reach for full live infra for those. Phase 3.5 hand-rolling an entire `graphql-ws` protocol client to prove one subscription push is the example of this going too far.
- Don't blindly re-run every earlier phase's full verification as a "regression check" — a targeted smoke test of the flows most likely to have been touched is enough; trust what previous phases already proved and committed.
- Skip worktree isolation / full background-agent delegation for small, low-risk changes — just edit directly. Reserve it for genuinely large, self-contained chunks of work.
- This is about cutting orchestration/testing overhead, **not** about writing less of the "why" documentation (`docs/DECISIONS.md`, per-service/per-module READMEs) — keep writing those exactly as thoroughly as before; that's the actual point of this project.
- **A new `isolation: worktree` agent's branch point can be stale relative to local `main`** — nothing in this repo has ever been pushed, so a worktree that branches from `origin/main` starts behind whatever the most recent locally-merged phase added, even when the spawning prompt says "phase N is done." The symptom (seen in Phase 5): the new branch's diff against `main` shows large *deletions* of files a prior phase added, and touches shared files (`docs/DECISIONS.md`, `backend/Makefile`) that a later phase also touched independently. Before merging any phase's branch, diff its file list against `main` and sanity-check nothing recently-merged is missing — if it is, `git rebase main` inside the branch's own worktree (not a plain merge) and resolve any conflicts by keeping both phases' additions, rather than merging the stale branch as-is.

## Don't

- Don't add a database-per-service via multiple Supabase projects — one instance, schema-per-service, per-service Postgres roles (see `docs/DECISIONS.md`).
- Don't have jobs-service call users-service's database or a synchronous RPC for skill data — it consumes `user.skills.updated` off Kafka into its own snapshot table instead.
- Don't wire real email sending into notification-service — it logs/records only, by design.
